# 敌人对话与潜行调查方案（v1，待评审）

## 目标

一套服务于**潜行调查**的敌人对话系统：敌人之间会交谈，玩家必须潜行靠近、在不被发现的
前提下**偷听**，从台词里捕获**关键词**换取情报，情报再解锁任务条件。

三条硬需求（来自需求方）：
1. 调用**声音系统**——对话即声音，能不能听到、听得多清由声音系统判定
2. 调用**任务系统**——台词内容取自任务信息，情报反过来推进任务
3. 负责**角色对话演出**，同时充当玩家潜行调查的**调查内容本体**

---

## 〇、设计哲学（最高优先级，后续所有取舍以此为准）

> **线索链由玩家自己构建。系统只提供碎片，不提供结论。**

具体约束——实现时任何一条都不能违反：

- **不做"任务更新"式提示。** 绝不出现「你获得了情报：地下室 2 点换班」这类把答案
  直接说出来的提示。系统只如实记录**玩家听到了什么**，解读交给玩家。
- **提示来自角色自身的思考，不是系统播报。** 关键词勾起的是**玩家角色的一句心声**，
  疑问式、不下结论（详见第四节）。
- **碎片本身不自动连线。** 线索本只按时间/地点罗列听到的原话，**不分组、不高亮关联、
  不画关系图**。把"这两句能对上"的发现权留给玩家。
- **要求联想与跳跃。** 单条碎片应当是**不完整**的——需要与另一段对话、某个场景物件或
  任务信息拼合才有意义。设计台词时刻意留缺口。
- **距离决定清晰度。** 站得越近听得越清楚。这是**风险与信息量的交换**，也是让"同一句话"
  能产出不同层级碎片的关键机制（见第三节）。
- **旗标是静默的。** `StoryFlag` 只用来**悄悄打开**后续可能性（新对话、可交互对象），
  不用来向玩家播报"你已解锁"。玩家应当靠推理去尝试，而不是靠系统指路。

## 二、核心玩法环

```
敌人结伴 ──► 按回合逐句说话 ──► 每句 SoundEmitter.Emit(Voice, 半径)
                                        │
玩家潜行靠近（不能被看见） ──► 自己的 SoundPerception 收到
                                        │
                     按 Confidence 分档 ──► 听到的【清晰度】不同
                                        │
                   碎片如实记入线索本（不解读、不连线）
                                        │
                  捕到关键词 ──┬─► StoryManager.SetFlag（静默，给系统）
                              └─► 角色内心独白（疑问式，给玩家）
```

**两重张力**：
- **回合制**：一段对话可以跨多个回合，玩家必须在附近**多待几个回合**且不被发现。
  跨几回合由每段对话的 `linesPerTurn` 决定（见下）。

> ⚠ **节奏修正**：原设计是固定**每回合一句**，前提是说话的人站着不动。
> 后来定了**说话不占用行动**——敌人边聊边巡逻，一段 5 句的对话拖 5 个回合，
> 说到一半人就走散了。所以改为每段对话自己配 `linesPerTurn`：
> 敌人回合开始时按 `secondsPerLine` 的间隔连说几句，再停到下一回合。
>
> | 用途 | `linesPerTurn` | 效果 |
> |---|---|---|
> | 闲聊 | `0` | 一口气说完（几秒钟），像路过时的随口几句 |
> | 情报对话 | `2` 左右 | 仍跨几个回合，保留"蹲守"的张力，但不至于拖到人走散 |
- **距离**：站得越近听得越清楚 —— 但也越容易被发现。**风险换信息量**。

### 清晰度三档（核心机制）

> ⚠ **实现时修正**：原本打算直接拿 `PerceptionEvent.Confidence` 当清晰度，但那个值是
> `1 - 距离 / **听力范围**` —— 意味着把听力练得越好，同一段话就听得越清楚，这不对。
> 实际改成**两道独立的闸**：
>
> | 参数 | 属于 | 决定 |
> |---|---|---|
> | `SoundPerception.hearingRange` | 听者 | 这一声**能不能到达我**（沿用现成链路，不改动） |
> | 三个半径（见下） | 这段对话 | 到达后听得**多清楚** |
>
> 于是听力好只会让你**更早察觉「那边有人在说话」**，不会让你听懂更多——
> 想听懂，只能走近。风险换信息量的交换因此才成立。

每段对话用**三个半径**分档（由近到远，写乱会被自动夹成单调递增）。
拆成三个是为了让**察觉范围远大于听懂范围**：玩家老远就知道那边有人在聊，
再自己决定要不要冒险贴上去。

| 档位 | 距离 | 玩家听到的 | 产出 |
|---|---|---|---|
| **清晰**（贴近，危险） | ≤ `clearRadius`（默认 6） | **完整台词**，含上下文 | **理解**这句在说什么 |
| **模糊**（中距） | ≤ `keywordRadius`（默认 10） | **只有关键词可辨**，其余遮成「…」<br>例：`……地下室……归你` | **静默触发旗标**；<br>浮出**角色内心独白**（见第四节） |
| **极模糊**（远处） | ≤ `audibleRadius`（默认 15） | 只知道「有人在低声交谈」+ 方位 | 只有方位，无内容 |
| 听不到 | 更远 | — | — |

> ⚠ **2026-10-06 调整**：三档从 `2.5/5/9`（部分文件 `3/6/10`）统一改为 **`6/10/15`**，
> 46 个对话文件全部同步。原值实测太近——玩家要贴到 2.5 米才听得懂台词，
> 在回合制潜行里几乎等于必被发现。
>
> **连带要求**：`audibleRadius` 现在是 15，而玩家 `SoundPerception.hearingRange` 默认 10，
> 因为实际察觉范围取两者较小值，10~15 米这一段极模糊档会被**整段吞掉**——
> 玩家会从"什么都没有"直接跳到"能辨出关键词"，失掉"察觉范围远大于听懂范围"的设计属性。
> 改三档时必须同步把玩家的 `hearingRange` 抬到 ≥ 15。

实际察觉范围 = `min(玩家 hearingRange, audibleRadius)`。距离从玩家**耳朵**量到说话者**嘴**——
从脚底量会把 1.6 米的垂直差算进去，让水平贴近 2 米时实测 2.56 米，悄悄超出清晰半径。

### 隔墙降档

耳朵到嘴之间**每隔一堵墙（Obstacle 层）降一档**：清晰 → 模糊 → 极模糊 → 听不到。

- 贴着厕所隔间外只能抓到关键词，**得绕进去才听得清**——关卡结构本身成了难度。
- 关着的门若在 Obstacle 层上，自然也会挡声；开门后不挡。
- 耳朵用**固定高度**（1.5 米），不随姿态降低。否则蹲在矮墙后，矮墙反而会挡在耳朵和嘴之间，
  出现"蹲下藏好 = 听得更差"的反直觉结果。
- 数墙用**逐面前进的射线**，不用 `RaycastAll`：后者每个碰撞体只报一次，
  整栋建筑外壳做成一个 MeshCollider 时，穿过三面墙也只算一堵。
- 必须忽略 trigger：本项目开着 `queriesHitTriggers`，区域触发器会被当成墙。

下蹲/匍匐时按**近 15%** 来算距离（`crouchDistanceFactor` 0.85）——屏息贴墙偷听。

### 飘字的锚点

模糊及以上的飘字锚在**说话者**头上（离得够近，知道是谁在说）。
**极模糊锚在玩家身边**、朝声源方向偏 1.5 米——察觉半径有 10 米，锚在声源会把
迷雾里敌人的精确位置暴露出来，而极模糊只该给方位。

设计要点：
- **旗标在「模糊」档就触发**——符合"关键词触发、玩家需要听到"。
- **贴近的回报是"上下文"而不是"更多旗标"**：你靠近换来的是**看懂这句话的意思**，
  从而能推理；系统不会因为你更近就多告诉你一条结论。
- 同一句话在不同距离听到会产出**不同层级的碎片**。飘字是实时字幕，**每次听到都显示**——
  同一对人隔 20 回合再聊一遍，站在旁边就该看到字幕。只有**旗标和内心独白每句只触发一次**。
- 刻意让「模糊」档的关键词**单独看不成立**——`地下室` 三个字本身没有信息，
  必须和另一段对话里的 `两点换班` 拼起来才有意义。**这就是留给玩家的联想缺口。**

## 三、数据格式（JSON，放 `Resources/Dialogues/`）

选 JSON 的理由：符合 `MissionData` 里已写明的「文件路径」，也和行为树 JSON 驱动的做法一致，
改台词不必进 Unity。

```jsonc
{
  "id": "guard_shift_talk",
  "mode": "turn",              // turn = 按回合推进（潜行对话）；realtime = 计时播完（任务演出）
  "linesPerTurn": 2,           // turn 模式下每个敌人回合连说几句；0 = 一口气说完
  "secondsPerLine": 2.5,       // 句与句之间隔几秒
  "clearRadius": 2.5,          // ≤ 此距离听到完整台词
  "keywordRadius": 5,          // ≤ 此距离能辨出关键词（旗标与独白在这一档触发）
  "audibleRadius": 10,         // ≤ 此距离察觉有人在说话；也是硬截断
  "alertsOthers": false,       // true = 以 Alert 发声，会惊动其它敌人（警戒喊话用）
  "repeatable": true,
  "cooldownTurns": 10,

  // ── 发起方式 ──
  "trigger": "manual",         // manual = 只能被显式 Play；ambient = 交给闲聊导演随机挑
  "weight": 1.0,               // ambient 抽签权重
  "topic": "换班",             // 话题标签，纯给编剧分类用，系统不解读
  "maxSpeakerDistance": 3,     // ambient：两人相距多少米以内才可能开聊
  "state": "idle",             // idle = 只在空闲时；alerted = 只在听到动静、正在查看时；any = 都行。战斗中一律不聊

  // 可选：复用 ConditionEvaluator，按任务/旗标/回合决定这段对话是否可用
  "conditions": [
    { "target": "StoryFlag", "key": "power_on", "op": "Equals", "value": "true" }
  ],

  "speakers": ["E01", "E02"],  // 参与者，用任务系统里的单位 id

  "lines": [
    { "speaker": "E01", "text": "换班还有多久？" },

    { "speaker": "E02",
      "text":    "两点。地下室今晚归你。",   // 清晰档：完整台词
      "blurred": "……地下室……归你",          // 模糊档：只剩关键词（留空则自动遮蔽）
      "keyword": "地下室",                   // 模糊档能辨出的词；触发提示与旗标
      "hint":    "这栋楼……有地下室？",        // ★ 玩家角色的内心独白（见第四节）
      "flag":    "intel_basement_shift" },

    { "speaker": "E01",
      "text":    "钥匙在老张那儿。",
      "blurred": "钥匙……",
      "keyword": "钥匙",
      "hint":    "谁会随身带钥匙？",
      "flag":    "intel_key_holder" }
  ]
}
```

### 名字也是线索：「？」→ 名字

说话人一开始显示 **「？」**。**敌人的名字本身就是关键词**：
玩家在模糊档及以上捕到了某人的名字，那个人的「？」就变成名字，之后他说的每句都带着名字。

- 每个敌人叫什么，统一写在 **`Resources/DialogueSpeakers.json`**（和台词一样在文件里改）：
  `{ "speakers": [ { "id": "E02", "displayName": "小刘" }, … ] }`。
  `DialogueSpeaker.displayName` 在 Inspector 里填了会覆盖文件里的。
- 台词里写 `{E02}` 或 `{B}`，发声时替换成那个人的名字。
- `"keyword": "{E02}"` —— 关键词整个就是一个名字占位符时，自动当作 E02 的名字，捕到就学会。
- **名字可以变**：先听到别人叫他"小刘"，后来听到有人叫他"刘队"——
  写 `"keyword": "刘队", "nameOf": "E02"`，捕到后他的名字就换成"刘队"。
- 已经飘在屏幕上的「？」会在学到名字的**那一刻当场变过来**。

```jsonc
{ "speaker": "E01", "text": "{E02}，换班还有多久？", "keyword": "{E02}" }   // 学到 E02 叫小刘
{ "speaker": "E01", "text": "为什么？刘队。", "keyword": "刘队", "nameOf": "E02" } // 小刘 → 刘队
{ "speaker": "A",   "text": "{B}，借个火。",       "keyword": "{B}" }        // 闲聊：B 是谁就学谁的名字
```

⚠ **一句只有一个关键词**：一句话没法既报名字又埋情报（`{B}，钥匙在老张那儿` 只能二选一）。
需要两个就拆成两句。

### 角色位：闲聊是随机配对的

任务演出里 `lines[].speaker` 直接写单位 id（`E01`），场上找谁说话一目了然。
但**闲聊的两个人是临场凑的**，不可能预先写死是谁。所以 `speaker` 一律当作**角色位**：

- `"speakers": ["E01","E02"]` —— 角色位名就是单位 id，按 id 去场景登记表里找人（任务演出）
- `"speakers": ["A","B"]` —— 抽象角色位，由闲聊导演把随机凑到一块的两个敌人绑上去

```jsonc
{ "id": "idle_meal", "trigger": "ambient", "topic": "吃饭", "weight": 1.0,
  "clearRadius": 2.5, "keywordRadius": 5, "audibleRadius": 9, "maxSpeakerDistance": 3,
  "speakers": ["A", "B"],
  "lines": [
    { "speaker": "A", "text": "你晚上吃了没？" },
    { "speaker": "B", "text": "食堂那个卤蛋又没了。" }
  ] }
```

闲聊照样可以埋 `keyword`/`hint`/`flag`——**玩家没法从外部判断哪段值得听**，
只能都听。这正是风险成本的来源。

要点：
- **关键词绑定在「句」上**，不是整段。一段对话可埋多条碎片，各自独立结算。
- `text` / `blurred` 对应清晰、模糊两档；`blurred` 不填时由系统**自动遮蔽**——
  保留 `keyword`、其余替换为「…」。手写 `blurred` 是为了让编剧能精确控制
  "漏出多少"，这直接决定玩家需要多大的思维跳跃。
- `flag` 是写进 `StoryManager` 的键，任务条件用 `ConditionTarget.StoryFlag` 读它。
  **它是静默的**——只打开后续可能性，不向玩家播报（见设计哲学）。
- ⚠ 编剧约束：**`keyword` 单独看应当不足以得出结论**。`地下室`、`钥匙` 这种孤立名词
  才是好碎片；`地下室两点换班钥匙在老张那儿` 这种把答案塞进关键词里的写法违背设计哲学。

## 四、提示 = 玩家角色的内心独白

> **提示不是系统在播报，是角色在想事情。**

捕到 `keyword` 时，浮出的不是「你获得了情报」，而是**玩家角色自己的一句心声**——
某个念头被这个词勾起来了。

语感参照：内陆帝国、天人感应那种「某种思维对这个关键词起了反应」。
⚠ **明确不做思维/技能系统**——这里只借用「提示来自角色自身思考」这个**呈现框架**，
不实现任何思维人格、技能检定或分支。

### 为什么这个设计成立

它一次解决两个问题：

1. **去权威化。** 角色的一句疑问是**主观的**，玩家不会把它当成系统盖章的确定情报，
   因此不违反「系统只提供碎片，不提供结论」。
2. **示范"联想"这件事本身。** 角色演示了「这个词让我想到什么」的动作，
   教会玩家该怎么玩，**但不给出答案**——想到什么、能不能和别的碎片对上，还是玩家的事。

### 编剧铁律

**提示只能提出疑问或引出联想，绝不能给结论、绝不能指路。**

| | 例子 | 判定 |
|---|---|---|
| ✅ | 「这栋楼……有地下室？」 | 开了个口子，玩家自己去想 |
| ✅ | 「谁会随身带钥匙？」 | 把注意力引向"人"，但没说是谁 |
| ✅ | 「两点。这个时间点我好像在哪儿见过。」 | 暗示存在另一条碎片，不说是哪条 |
| ❌ | 「地下室 2 点换班，去那儿看看。」 | 系统替玩家想完了 + 指路 |
| ❌ | 「看来钥匙在老张身上。」 | 给了结论，玩家不用推理了 |

补充约束：
- **不是每条 keyword 都要配 `hint`。** 留白本身也是设计——有些碎片就该沉默地躺在
  线索本里，等玩家自己撞上。滥用提示会把游戏做成带旁白的任务列表。
- 提示是**第一人称、口语化的短句**，不超过一行。它是个念头，不是分析。

### 与 `flag` 的分工

| 字段 | 给谁 | 作用 |
|---|---|---|
| `hint` | **玩家看** | 角色想到了什么（主观、疑问、无结论） |
| `flag` | **系统用** | 静默打开后续可能性（新对话、可交互物、任务条件） |

两者由同一个 `keyword` 触发，但**互不代替**。
⚠ 特别注意：**不要让 `hint` 去描述 `flag` 做了什么**——
「我好像可以去查地下室了」就是把静默旗标播报出来了，等同于任务更新提示。

### 呈现

- 与对话字幕**样式区分**：无说话人名、斜体或括号、不同颜色，出现在**玩家角色**附近
  或屏幕下缘固定位，不跟随敌人。
- 触发档位：**模糊档及以上**（与 `flag` 同时机）。极模糊档听不出词，自然也没有提示。
- 线索本里，「听到的原话」与「想到的」**分开记录、样式区分**——
  前者是证据，后者是角色的主观反应，不能混为一谈。

## 五、运行时架构

```
DialogueManager（单例）
  · Play(key, context)                填上 GameManager / MissionData 的预留调用
  · 从 Resources/Dialogues/<key>.json 加载并缓存
  · 按 mode 驱动推进：turn = 敌人回合开始时发放 linesPerTurn 句额度，按秒连说；realtime = 按秒说完
  · 若开播时正是说话阵营的回合（闲聊导演就是这时开聊的），立刻开口；否则等到他们的回合
  · 每说一句：SoundEmitter.Emit(说话者位置, Voice/Alert, audibleRadius, 说话者, tag=lineId)
  · 维护冷却、conditions 判定、防止同一组敌人同时开多段对话

DialogueSpeaker（挂敌人）
  · 提供 speakerId（对应任务里的 E01/E02）
  · 说话时：转向对话对象、触发 Animator（可选）、由 Manager 代为发声

EavesdropListener（挂玩家）
  · 订阅玩家自己的 SoundPerception.OnPerceptionEvent
  · 收到 Voice 事件 → 用 tag 取回台词，用 Confidence 定清晰度档位
  · 清晰 → 完整原话；模糊 → blurred 文本；极模糊 → 只记「有人交谈」+方位
  · 捕到 keyword（模糊档及以上）→ 静默 SetFlag + 抛出 hint（内心独白）
  · 把结果交给 ClueLog 记录，并交给 DialogueUI 显示

AmbientChatDirector（对话导演）—— **所有对话都由它自动开，不需要按键或外部调用**
  · 每个敌人回合扫一遍所有 trigger = ambient 的对话，静默筛掉冷却中 / 条件不满足的，
    再找出"现在凑得齐人"的，按 weight 抽一段开播
  · 角色位是**真实单位 id**（["E01","E02"]）→ 只能由这几个人聊：他们碰头、都不警觉时才会聊。
    **情报对话就这么写**——E01 和 E02 碰头时才说起换班的事
  · 角色位是 **A / B** → 从附近空闲的人里随便凑。**闲聊就这么写**
  · 可以混写（["E02","A"]）：E02 和他身边随便哪个人聊
  · 有人进入警觉（看到玩家 / 正在查动静）→ 立刻掐掉那段对话
  · ⚠ 只负责"让他们开口"，从不碰 AP / 黑板 / 行为树

DialogueUI（UGUI + UI.Text，非 TMP；画布与字体可留空自动创建）
  · **玩家看得到的所有固定文字都在它的 Inspector 里**：「？」、名字前缀格式、方位词、
    "有人在低声交谈"、自动遮蔽的「……」、独白括号，以及三档颜色、字体
  · 偷听逻辑（EavesdropListener）只判档、给方位编号，不拼任何显示文字
  · 台词【飘字】：锚在声源上方，随时间上浮淡出，按档位变样式。
    只显示玩家真的听到的内容——没听到的什么也不画，
    玩家永远不知道自己漏掉了什么"具体内容"，只知道"漏掉了"
  · 内心独白走【独立通道】：屏幕下缘、无说话人名、括号包裹、颜色区分（见第四节）
```

> **线索本（ClueLog）本轮不做。** 玩家看到的就是当场的飘字。
> `EavesdropListener` 内部仍记「这句听到过哪一档」，用于更近处重听时升级飘字、
> 并避免同一句反复打扰。设计保留在本文档里，要做时再加。

### 声音系统改动（小）

1. `SoundType` 增加 **`Voice`**。
2. `SoundEvent` / `SoundEmitter.Emit` 增加**可选 `tag` 字段**（string），
   `SoundPerception` 原样透传到 `PerceptionEvent.Tag`。
   > 这样偷听方能知道"听到的是哪一句"，而**音频可达性判定完全复用现有实现**，
   > 不需要在对话系统里重写一遍距离/楼层/遮挡逻辑。
3. `SoundPerception` 的 `ignoreOtherEnemySound` 目前会过滤掉**所有**来自 Enemy 的声音。
   改为**只过滤 Movement 与 Voice**，放行 `Alert`——这样普通闲聊不会互相惊动，
   而"警戒喊话"（`alertsOthers: true`）能引来同伴。

## 七、实施分期

> ### 零配置：场景里什么都不用挂
>
> `DialogueBootstrap` 在进入 Play 时自动补齐缺的组件：`StoryManager`、玩家的
> `SoundPerception` + `EavesdropListener`、每个敌人的 `DialogueSpeaker`（id 取 `enemyId`）、
> 以及挂着 `DialogueManager` + `AmbientChatDirector` + `DialogueUI` 的 `DialogueSystem` 物体。
> 已经手动挂了的不动，只在运行时补，不改场景文件。
>
> 为什么要它：这套系统要六种组件分挂在四类物体上，漏一个（忘了 `StoryManager`、
> 或者在 Play 模式下加的组件停止后丢了）整套就悄无声息地不工作——这正是第一次测试"完全没效果"的原因。
>
> ### 每个敌人都会自己开口
>
> 只靠两人碰头，敌人分散时就一直冷场（测试场景一楼的 E01、E02 相距 28 米，永远碰不上）。
> 所以每个敌人都有**单人台词**：空闲时自言自语、对着对讲机说话；听到动静过来查看时嘀咕。
>
> | id | 名字 | 空闲自言自语 | 查动静时嘀咕 | 两人对话 |
> |---|---|---|---|---|
> | E01 | 老王 | 6 | 2 | 与 E02 三段 |
> | E02 | 小刘（刘队） | 6 | 3 | 与 E01 三段 |
> | E03 | 阿强 | 6 | 2 | 与 E04 三段 |
> | E04 | 大陈 | 6 | 2 | 与 E03 三段 |
> | 任何人 | — | — | 2 | 通用闲聊五段 |
>
> 共 46 段。线索按设计哲学拆成碎片分散在各人嘴里（两点、地下室、钥匙、老周"调走了"、
> 夜里的车、开着的窗、对讲机里的陌生声音、没人值守的监控室），单独一条都拼不出结论；
> 名字也是线索（老王嘀咕"小刘那孩子……"，玩家就知道了 E02 叫什么）。
>
> 导演默认每个敌人回合都让能开口的人开口（`chancePerTurn` 1、`globalCooldownTurns` 0、
> `maxConcurrent` 4），战斗中一律不说。

## 八、待定 / 风险

- ~~**字幕呈现**~~ → **已定：世界空间飘字**（锚在声源上方，上浮淡出）。
  在"极模糊档只知道方位"的设计下，飘字的定位感是必需的。
  内心独白固定在玩家侧屏幕下缘，不跟敌人走。
- ~~**线索本**~~ → **本轮不做**。玩家看到的就是当场的飘字。要做时设计仍在第五节。
- ~~**闲聊怎么发起**~~ → **已定：先做涌现式**（两个空闲敌人靠近就可能开聊）。
  场景标记式的「聊天点」（抽烟角落、饮水机）之后再加——
  好处是玩家能学会"哪里能蹲到情报"，把偷听变成可规划的目标。
- ~~**对话期间敌人的行为**~~ → **已定：说话不占用回合内的行动**，聊天与行动互不干扰。
  代价是没法用"他们站着聊天"来制造固定的偷听窗口——这个缺口留给日后的聊天点来补。
- **提示是否随已知信息演进**：同一个 `keyword`，在玩家已经掌握别的碎片后，
  角色的心声可以不一样（`hints` 带 `requires` 条件，取第一条命中的）。
  ⚠ **风险**：演进版提示很容易滑向「替玩家连线」——
  「地下室……是老张钥匙开的那个？」已经把两条碎片拼好了。
  若要做，必须坚持**演进后的提示仍然是疑问句、仍不给结论**。
  保守做法是 Phase 1 先只做静态 `hint`，验证手感后再议。
- ~~**隔墙偷听**~~ → **已定：每隔一堵墙降一档**（见第二节）。
- ~~**察觉与听懂是否拆开**~~ → **已定：三个半径**（clear / keyword / audible）。
- ~~**演出接口（音频/说话动作）**~~ → **本轮不接**，等机制手感调好、资源就绪再说。
- ~~**闲聊冷却粒度**~~ → **已定：保持全局**。一对人聊过「吃饭」，短期内全场都不再聊，
  防止同一段台词反复刷屏。
- **三个半径的数值**：2.5 / 5 / 9~10 只是起手值，直接决定"要多冒险才能听懂"，需实测。
  下蹲的距离折算（0.85）与墙体降档（每墙 1 档）同样待实测。
- **对话频率**：按需求方要求改为**每回合都有人在聊**——`chancePerTurn` 1、
  `globalCooldownTurns` 0、`maxConcurrent` 2；开聊距离放宽到 5 米、闲聊冷却 4 回合。
  注意对话池要够大：每段都有自己的冷却，池子里只有三五段时，很快会全部进冷却而冷场。
  想要"一直有人说话"，就多写几段 ambient 对话。
- **同一段对话能否重复偷听**：`repeatable` + `cooldownTurns` 已预留。若允许重复，
  玩家可以"先远听拿碎片、再冒险近听拿上下文"，这正是风险换信息的核心循环。
